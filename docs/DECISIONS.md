# Design decisions

- **Local development:** use atomic file-backed state and JSONL logs when database URLs are absent, so a clean checkout runs without Docker or separately installed databases. `DATA_DIR` controls the local storage directory.
- **Production storage:** PostgreSQL and MongoDB are both required and startup fails closed if either cannot be reached. PostgreSQL TLS verifies certificates; MongoDB uses TLS. Mongo log documents have a 14-day TTL. Local file adapters are development/demo tools, not a production failover mode.
- **PostgreSQL shape:** use a versioned migration runner and keyed `app_records` JSONB table for the current single-clinic deployment. Migrations also create shared rate-limit counters and queue/idempotency indexes. This is not a normalized, multi-tenant clinical data model; the deployment boundary is one clinic per installation.
- **MediBook contract:** develop against the included mock because no real service contract or credentials were supplied. The API base URL and service key remain configurable; production requires HTTPS and rejects redirects.
- **Widget proxy:** browser embeds call MediAssist's public API. This keeps the MediBook service key server-side and does not depend on the clinic system supporting browser CORS.
- **Authentication and request controls:** JWTs use a fixed signing algorithm, issuer, audience, and session version. Production sessions expire after one hour; password changes revoke prior sessions. Login, event, note, and widget limits use shared PostgreSQL counters in production and in-process counters for local development.
- **Event idempotency:** signed event receipts are durable, leased across instances, and bound to a keyed payload hash. Reusing an event key with a different payload returns a conflict. Event automation payloads drop common sensitive fields and use best-effort redaction before an LLM request.
- **Webhook delivery:** delivery state remains durable in structured storage; each attempt is an append-only Mongo log record. PostgreSQL claims use row locks and expiring leases so multiple replicas do not process the same delivery concurrently. Outbound HTTPS destinations are checked against DNS, private/reserved addresses are rejected, the selected address is pinned for the request, and redirects are not followed.
- **Logging:** request and integration logs contain correlation IDs and operational metadata; clinical note text, bearer tokens, and secrets are excluded. In production MongoDB failure is surfaced rather than silently switching to local logs.
- **LLM behavior:** deterministic mock summaries are the default for local development. Production requires a configured real provider. Note text is redacted before the provider call, but regex redaction can miss identifiers and model output must be reviewed by a clinician.
- **Privacy and compliance:** these controls are engineering safeguards, not a HIPAA or other compliance claim. Do not use real patient data until provider agreements, clinic data policy, access boundaries, retention, backups/restores, monitoring, and incident response have been reviewed.
- **Deployment:** Render/Neon/Atlas/Vercel are examples, not live dependencies. Hosting accounts, the real MediBook contract, provider credentials, backups, and operational controls must be supplied and verified separately.
